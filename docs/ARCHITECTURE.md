# Архитектура и воспроизводимый запуск

## Что входит в работающий продукт

- `artifacts/robotshub/src/` — React-приложение с маршрутизацией Wouter, состоянием проекта и расчётами в браузере.
- `artifacts/robotshub/public/` — данные карты, документы кейсов, изображения и другие ресурсы, доступные по URL.
- `artifacts/robotshub/src/data/` — каталог решений и шаблоны объектов. Приложение не запрашивает базу данных для этих данных.
- `Dockerfile` — сборка в Node.js 24 / pnpm 10.26.1 и выпуск статических файлов через nginx.
- `compose.yaml` — сервисы `web` и `news`, наружу открыт только порт `web` (по умолчанию 8080); `deploy/nginx.conf` — SPA fallback, прокси новостей и `/healthz`.
- `deploy/news.Dockerfile` — автономный Express/SQLite-движок новостей с проверкой `/healthz` и постоянным томом `news-data`.

Схема: браузер → nginx → HTML/JS/CSS/JSON/изображения; для `/news`, `/api/news` и `/admin-news` — nginx → движок новостей. Расчёты и пользовательские параметры обрабатываются в браузере; проект сохраняется в localStorage этого браузера. Публикации новостей и их статусы хранятся отдельно в SQLite. `/sitemap.xml` связывает статическую карту `/sitemap-pages.xml` с динамической `/news/sitemap.xml`; отдельные опубликованные саммари доступны по `/news/:id`.

## Отдельный каркас API

Полный API из `artifacts/api-server/src/index.ts` требует PostgreSQL (`DATABASE_URL`). Для Compose используется другой вход: `src/news-engine/server/news-server.js`, который не импортирует PostgreSQL и запускает только существующий движок новостей. Порт 8099 доступен только внутри сети Compose. По умолчанию токен модерации не задан и административные операции запрещены. Для модерации можно передать необязательный `ADMIN_TOKEN` через окружение.

Том `news-data` сохраняет базу после пересоздания контейнера; `docker compose down` его не удаляет, `docker compose down -v` уничтожает данные. Для резервного копирования SQLite используйте согласованную копию (SQLite backup API либо остановленный сервис), а не только файл `news.db` при активном WAL. Начальный запуск создаёт пустую базу, но не импортирует публикации из другого размещения автоматически.

## Параметры

| Где | Параметр | Значение по умолчанию | Назначение |
| --- | --- | --- | --- |
| Docker Compose | `WEB_PORT` | `8080` | Порт на компьютере проверяющего |
| Vite (локально) | `PORT` | `5173` | Порт сервера разработки |
| Vite (локально) | `BASE_PATH` | `/` | Префикс URL при специальной сборке |

Docker всегда собирает для `/` и обслуживает приложение на корне сайта. Для размещения под подкаталогом нужна отдельная сборка с согласованными `BASE_PATH` и конфигурацией веб-сервера; текущий Compose поддерживает корень сайта. Никаких обязательных секретов для описанного веб-приложения нет.

## Ограничения доказательности

Карта объединяет исходные отраслевые записи и пересекающиеся тематические подборки; тематические счётчики не прибавляются к общему количеству. Отраслевая принадлежность решения не доказывает применимость к конкретной площадке. Экономика рассчитывается только в пределах модели операции и доступных исходных параметров; отсутствие валидированной модели показывается явно, а не заменяется общим шаблоном.

Подробное описание входных данных, построения сцены, работы движка и ограничений: [как устроена симуляция `/simulation`](simulation-internals.md).

## Кабинеты и заявки в Compose

Тот же автономный сервер обслуживает `/cabinet`, `/lead`, `/api/cabinet` и `/api/leads`. nginx передаёт эти маршруты без изменения пути. При первом запуске копия `solutions.json` помещается в `/data/news/catalog.json`; последующие запуски сохраняют её. SQLite и этот JSON находятся в одном постоянном томе. Дополнительные необязательные переменные `ADMIN_EMAIL` и `ADMIN_PASSWORD` создают начального администратора кабинета; рабочие значения не входят в репозиторий.

Статический frontend использует JSON на момент сборки. Одобрение драфта в кабинете изменяет только серверный JSON; для переноса в публичные карточки нужен отдельный выпуск исходных данных и пересборка. Содержимое тома не должно автоматически перезаписываться при обновлении образа.

После сборки `deploy/build-nginx-config.mjs` превращает `dist/seo-rewrites.json` в точные nginx locations для SEO-оболочек, перед общим SPA fallback. Результирующая конфигурация входит в образ; вручную поддерживать сотни маршрутов в nginx не требуется.
