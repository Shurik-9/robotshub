# Передача проверяющим через GitHub

## Порядок действий ответственного за репозиторий

1. Получите согласование владельца проекта по составу передаваемых материалов и правам на ресурсы из [DATA_AND_RIGHTS.md](DATA_AND_RIGHTS.md). Для первичной проверки используйте **закрытый** GitHub-репозиторий.
2. Из исходной рабочей папки запустите:

   ```bash
   bash scripts/export-review-repo.sh ../robotshub-review
   cd ../robotshub-review
   docker compose up --build --wait
   curl -f http://localhost:8080/healthz
   docker compose down
   ```

3. Проверьте содержимое копии: в ней не должно быть `.git`, `.agents`, `.replit`, `.replit-artifact`, `.env` с секретами, `attached_assets/` или полных текстов `research/sources/`. Просмотрите список файлов и права на всё в `artifacts/robotshub/public/`.
4. Создайте пустой закрытый GitHub-репозиторий без автоматически добавленных README/.gitignore. В **копии**, не в исходной рабочей папке:

   ```bash
   git init
   git branch -M main
   git add .
   git status --short
   git commit -m "Prepare RobotsHub reviewer release"
   git remote add origin <URL_НОВОГО_РЕПОЗИТОРИЯ>
   git push -u origin main
   ```

   Адрес репозитория и доступы предоставляются владельцем; скрипт ничего не публикует автоматически. Не копируйте Replit-remotes и старую Git-историю.
5. Дождитесь зелёной проверки GitHub Actions и попросите независимого проверяющего выполнить **только** команды Docker из README на чистой машине.

### Если загрузка через интеграцию не создала GitHub Actions

Некоторые GitHub-подключения разрешают записывать исходники, но не позволяют создать файл в `.github/workflows/`. В таком случае владелец репозитория должен в интерфейсе GitHub создать файл `.github/workflows/verify.yml` и вставить содержимое [verify-workflow.yml](verify-workflow.yml). После сохранения дождитесь зелёного прогона на вкладке Actions. **Пока файл не создан, автоматическая проверка в GitHub не работает** — локальная проверка Docker остаётся доступной по [VALIDATION.md](VALIDATION.md). При обычном `git push` с разрешением на workflows файл уже находится в экспортированной копии и этот шаг не нужен.

## Состав передачи и границы

Работающее веб-приложение поставляется вместе с необходимыми публичными ресурсами, тестами и документами. Экспериментальный API/БД-каркас остаётся в исходниках для полноты кода, но **не является зависимостью запуска**. Локальные проекты пользователя живут в браузере и не синхронизируются между проверяющими. Не утверждайте, что проверка расчетов подтверждает корректность исходных отраслевых данных.

При сбое проверяющему нужны `docker compose ps`, `docker compose logs --tail=100 web`, версия Docker/Compose, архитектура машины и адрес страницы. Не просите присылать токены или содержимое `.env`.
